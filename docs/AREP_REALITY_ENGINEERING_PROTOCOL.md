# Agentic Reality Engineering Protocol (AREP)
*Doctrine: Build the terrain so the agent cannot easily walk into nonsense.*

---

## 1. The Death of Prompt Engineering

Prompt engineering assumes that agent behavior is primarily a function of the language description provided in the system or user message:

$$\text{Output} = f(\text{Prompt})$$

For shallow, text-only operations (e.g., drafting emails, summarizing text), this equation is a tolerable approximation. However, for high-stakes, domain-specific operations (e.g., Earth systems, capital allocation, infrastructure, medicine, law), prompting fails. Language descriptions alone cannot capture the material structures, feedback loops, and physical constraints of professional workflows.

**Reality Engineering** replaces prompting by shaping the entire environment the agent wakes up inside:

$$\text{Output} = f(\text{Model}, \text{Prompt}, \text{Accessible Evidence}, \text{Tool Affordances}, \text{Schemas}, \text{Memory}, \text{Governance}, \text{Feedback Loop}, \text{Domain Ontology})$$

By engineering the substrate itself, we establish **geological attractors** where useful, grounded actions become the path of least resistance, regardless of prompt quality.

---

## 2. The AREP Framework

AREP structures agent interactions around four pillars:

### A — Affordance
What the agent is allowed and able to do. Tools must be clean, orthogonal, and bounded.

### R — Reality
The ground truth of the system: schemas, physical constraints, historical logs, databases, and enterprise evidence reservoirs (e.g., SharePoint/OneDrive).

### E — Epistemology
How the agent separates different classes of truth. It defines the Claim Ladder, ensuring the agent explicitly differentiates between observed, derived, and interpreted facts.

### P — Protocol
The rules of interaction: reproducibility mandates, verification loops, audit trials, and human-in-the-loop escalation paths (e.g., `888_HOLD`).

## 3. Comparison Matrix

| Dimension | Prompt Engineering | Reality Engineering (AREP) |
|---|---|---|
| **Primary Object** | Text instruction / wording | Operating environment / substrate |
| **Control Method** | Wording tweaks, few-shot examples | Schemas, tool affordances, permission scopes |
| **Failure Mode** | Confident hallucination | Missing evidence $\rightarrow$ `888_HOLD` |
| **Unit of Work** | Chat turn / prompt response | State transition / verified claim envelope |
| **Memory** | Ephemeral chat history | Multi-layer graph, hash-chained ledger (`Vault999`) |
| **Safety** | Slogans ("Be polite", "Do not hack") | Structural gates, sandbox limits, sovereign veto |
| **Grounding** | Parametric weights | Document repositories, raw databases, physics engines |
| **Success Metric** | Pleasing output text | Grounded, reproducible action with receipts |

## 4. GEOX as Earth AREP

GEOX does not merely prompt the agent to "think like a geologist." It constructs a geological reality:

1. **Physical Constraints:** Archie’s equation, density-neutron crossplots, and checkshot-time relation guards.
2. **Strict Schemas:** Every subsurface calculation must compile into a standardized `earth_memory_envelope`.
3. **Evidence Invariant:** All geological claims must carry a source reference, a version hash, and an epistemic classification.
4. **Governed Actions:** Prospect risk assessments and volume estimations require human validation and cannot be unilaterally sealed.

When an external agent interacts with GEOX, it cannot easily hallucinate because the boundary conditions of the terrain restrict it to physically plausible geological outcomes.
